# 压测与容量基准

> 全部数字来自本机实测（Windows 11 / Go 1.27.1 / PostgreSQL 17 本地实例 / 住宅带宽），
> 端点 `https://ethereum-rpc.publicnode.com` 免费档，标的合约为主网 USDC `0xA0b8...eB48`。
> 换端点（Alchemy / Infura 带 key）后应重测，绝对数值会明显不同。

测试日期：2026-11-16

---

## 1. 单次 eth_getLogs 的容量

publicnode **不限制单次返回的日志条数**。此前担心的「约 1 万条上限」并不存在：

| 区块跨度 | 日志条数 | 耗时 | 响应体 |
|---:|---:|---:|---:|
| 2000 | 139,910 | 39.9 s | 86.8 MB |
| 1000 | 66,061 | 10.4 s | 41.0 MB |
| 500 | 32,980 | 10.6 s | 20.5 MB |
| 200 | 13,082 | 5.6 s | 8.1 MB |
| 100 | 6,055 | 3.5 s | 3.8 MB |

USDC 的日志密度约 **65~70 条/块**，所以 2000 块批对应约 14 万条日志、近 100 MB 响应体。
真正的约束不是条数，而是**传输量与内存**。

另有一次同区间精确计时：`26422714..26424713` 单次请求 **41.65 s / 97.4 MB**。

## 2. 端点选择与历史窗口（关键约束）

### 2.1 各免费端点实测

三个维度都要测：归档查询、JSON-RPC 批量能力、单请求延迟。只测其中一个会选错端点。

| 端点 | 归档 `eth_getLogs` | JSON-RPC 批量 | 结论 |
|---|---|---|---|
| `ethereum-rpc.publicnode.com` | ❌ 仅最近约 8,000 块 | ✅ 100 个/批，4.4 s | **选用** |
| `eth.drpc.org` | ✅ | ❌ 最多 3 个/批 | 归档备选，与块头批量冲突 |
| `rpc.flashbots.net` | ✅ | ❌ 10 个即被拒 | 不适用 |
| `eth.llamarpc.com` | — | — | HTTP 525（TLS 握手失败） |
| `1rpc.io/eth` | ❌ `method not available` | — | 不可用 |
| `cloudflare-eth.com` | ❌ `Internal error` | — | 不可用 |

**没有任何免费端点同时满足「可查归档」与「支持批量」。**

本项目的块头获取依赖批量请求（2000 块 = 20 次 `eth_getBlockByNumber`，逐条则需 2000 次），
因此选 **publicnode**，并把演示区间限定在最近约 8,000 块。

若将来需要全量回扫：换 Alchemy / Infura 免费档（同时支持归档与批量），只改 `RPC_HTTP_URL`，
不需要动任何代码。若只是临时查历史，把 `RPC_HTTP_URL` 指向 `eth.drpc.org` 也能用，
但 `headerBatchSize`（100）会超出其免费额度，需要一并调整。

### 2.2 publicnode 的可用窗口

| 回溯距离 | 结果 |
|---:|---|
| 2,000 / 5,000 / 8,000 块 | ✅ 正常 |
| 10,000 / 12,000 块 | ❌ 归档请求被拒 |

免费档只能覆盖最近约 **8,000~9,000 块**（约 27 小时链上时间）。
这意味着索引器若停机超过一天，`next_block` 会落到窗口之外而失败——属于已知限制，
重启时把 `index_start` 拨到窗口内即可。

> **2026-11-17 修正**：`cmd/verify` 的二分探针实测边界为 **head − 9,999**（链头 26,433,602 时，
> 26,423,603 可回放、26,423,602 及更早被拒），即窗口约 **10,000 块**。上表把 10,000 判为
> 「被拒」，很可能是当时把 `fromBlock` 取成 `head−10000` 而 `toBlock` 取了 `head`，
> 实际跨度 10,001 块，正好越界。结论按 10,000 块记，但窗口是**滚动**的，
> 任何硬编码都会过期——工具里因此改成运行时二分探测，不写死宽度。

### 2.3 评估端点时的教训

第一轮只测了单请求能不能查归档，据此选了 drpc；等接入「块头批量请求」后立刻收到
`400 Batch of more than 3 requests are not allowed on free plan`。
端点评估必须把**实际调用模式**（批量大小、并发）一起测，否则结论不成立。

### 2.4 对项目的影响

HANDOFF 第 2 节要求的「从部署块到链头」全量回扫，在 publicnode 免费档上做不到
（窗口约 8,000 块），在 drpc 上可以但批量受限、在本项目里跑不动。

因此实际演示区间按「够用且有说服力」裁剪，而不是真跑全量。`RPC_HTTP_URL` 本来就是环境变量，
需要全量回扫时切换到 Alchemy / Infura 免费档即可，不改代码。

## 3. 端到端吞吐（批量大小的决定性影响）

| 批量 | 区间 | 日志条数 | 端到端耗时 | 单块耗时 |
|---:|---|---:|---:|---:|
| 2000 | 26422714..26424713 | 139,701 | 51.0 s / 59.5 s | **25.5 / 29.8 ms** |
| 10 | 26412000..26412009 | 678 | 1.36 s | 136 ms |
| 1 | 26424728 | 52 | 0.98 s | 977 ms |

同一数据量下，2000 块批比 10 块批快约 **5 倍**，比单块批快约 **35 倍**。
原因是固定开销（HTTP 往返、20 次块头批量请求、事务提交）被摊薄。

两次 2000 块批耗时 51.0 s 与 59.5 s，说明住宅带宽下网络抖动约 ±15%。

推算追平能力：约 **34~39 块/秒**。以太坊出块 12 秒/块即 0.083 块/秒，
索引速度是产出速度的 400 倍以上，追平链头无压力。

## 4. 资源占用

| 指标 | 数值 | 条件 |
|---|---:|---|
| 进程峰值工作集 | 463 MB | 2000 块批 / 139,701 条日志 |
| 进程峰值私有内存 | 492 MB | 同上 |
| 单次响应体 | 97.4 MB | 同上 |
| `chain_log` 总大小 | 53 MB | 142,599 行，含 3 个索引 |
| `decoded_event` 总大小 | 42 MB | 142,599 行，含主键 |

内存与批量基本线性相关。若换成日志密度更高的合约，2000 块批会成比例放大内存占用，
届时需要按预估条数而非块数切批。

## 5. 幂等性

2000 块批重扫同一区间（游标拨回 26422714）：

```
from=26422714 to=26424713 logs_fetched=139701 logs_inserted=0 decoded_inserted=0 headers_inserted=0
```

三张表行数不变。W1 验收项「同区间扫两遍行数不变」在最大批量下同样成立。

## 6. 解码覆盖率

| 指标 | 内置 ABI | Sourcify ABI |
|---|---:|---:|
| 已解码 | 140,238 | 16,018 |
| 未解码（`undecodable`） | 2,361（1.67%） | **0** |

两列来自不同区间，只作量级对照。决定性证据是同一段区间 `26426000..26426199` 的重扫对比：

| 阶段 | decoded | undecodable |
|---|---:|---:|
| 内置 ERC20 ABI | 15,781 | 237 |
| Sourcify 拉到实现合约 ABI | 16,018 | **0** |

237 条未解码全部是 USDC 自有事件，接上实现 ABI 后归零。事件分布：
`Transfer` 14,555、`Approval` 1,226、`Mint` 111、`Burn` 96、`AuthorizationUsed` 30。

注意：切 ABI 不会回溯重解已有数据。存量 `decoded_event` 仍是内置 ABI 的结果，
需要重解时按区间删除后回退游标重扫（本次验证即此做法）。

## 7. 本次压测修正的缺陷

`RequestTimeout` 原为 20 秒，而单次 2000 块请求实测 41.65 秒。
两者不匹配意味着每次大批次都会踩超时并触发近 100 MB 的重传。已上调至 **60 秒**。

## 8. 全量索引的时间估算

以 USDC 为例：部署块约 6,082,000，当前链头约 26,424,000，约 2,034 万块。

```
20,340,000 块 ÷ 37 块/秒 ≈ 550,000 秒 ≈ 6.3 天（不间断）
```

这解释了为什么 ADR-3 把地址画像改成「按需查询 + 缓存」而不是全量预计算，
也说明本项目适合「单合约 + 事件密度中等」的索引场景，不适合无差别扫描全链。

## 9. 重测（2026-11-17）

前面的数字取自 W1（2026-11-16）。数据密度变化后必须重测，否则 README 会引用过期结论。

方法：建独立库 `chainlens_bench`（不碰开发库），跑迁移后从 26,429,000 起索引，
取前两批完整 2000 块批的数字，测完即删库。

| 批量 | 区间 | 日志条数 | 端到端耗时 | 单块耗时 |
|---:|---|---:|---:|---:|
| 2000 | 26429000..26430999 | 179,662 | 112.7 s | 56.3 ms |
| 2000 | 26431000..26432999 | 156,039 | 99.0 s | 49.5 ms |
| 662（尾批） | 26433000..26433661 | 46,534 | 28.0 s | 42.2 ms |

- 单块平均 **约 53 ms**（两批合计 4000 块 / 211.7 s）
- 追平能力 **约 18.9 块/秒**，是出块速度的 150 倍以上
- 存储：383,426 条日志 → `chain_log` **147 MB** + `decoded_event` **113 MB**，约 **680 B/条**
- 新数据未解码率 **0%**（Sourcify ABI）

与第 3 节的对比：

| 指标 | 2026-11-16 | 2026-11-17 | 变化 |
|---|---:|---:|---|
| 单块耗时 | 25.5~29.8 ms | ~53 ms | **约 2 倍** |
| 追平能力 | 34~39 块/秒 | ~19 块/秒 | 减半 |
| 日志密度 | ~70 条/块 | ~84 条/块 | +20% |
| 存储/条 | ~666 B | ~680 B | 基本持平 |
| 未解码率 | 1.67% | 0% | — |

日志密度只涨了 20%，耗时却翻倍，说明单条成本本身上升了（同区间单次 `eth_getLogs`
的耗时也从 41.65 s 量级升到约 100 s）。**无法区分是端点限流、带宽波动还是端点侧负载**，
只能作为当前环境的事实记录。需要可复现的吞吐结论时，应换带 key 的端点在受控条件下重测。

## 10. 回放对拍（2026-11-17）

`cmd/verify` 用链上 `eth_getLogs` 回放核对库内数据，逐条比对
`(tx_hash, log_index)` 主键与全部字段（合约、topic0~3、data、block_time）：

```
汇总：19 批，链上 783,105 条，库内 783,105 条
  缺失 0，多余 0，字段不一致 0，block_time 不一致 0
结果：一致
```

- 覆盖库内 848,735 条中的 **783,105 条（92.3%）**
- 剩余 65,630 条（区间 26,422,714..26,423,602，共 889 块）超出归档窗口，无法回放，不计入判定
- 边界由二分探针在运行时确定，不写死窗口宽度

**这份对拍能证明什么**：索引器忠实记录了链上日志，没有丢、没有重、字段与块时间均未被篡改。
**不能证明什么**：我们对 USDC 语义的理解与第三方一致。Etherscan API 需 key（不接受代注册），
Blockscout 在本机网络不可达，因此**没有第三方交叉验证**。README 的「局限」一节已如实标注。

## 2026-11-23 P2 吞吐归因

### 结论

| 环节 | 占端到端耗时 | 绝对值 |
|---|---|---|
| 网络传输 | **98%** | 经本机代理 0.9–3.0 MB/s（波动极大） |
| `ethclient` 的 JSON 反序列化 | 1–2% | 3.7–4.2 µs/条 |
| `decoder.Decode`（ABI 解码） | <1% | 2.2–2.5 µs/条 |
| 写库（COPY + ON CONFLICT） | 未单独拆分 | 见索引器日志 `elapsed_ms` |

**瓶颈是传输，不是解析。** 这个结论推翻了此前「JSON 解析拖慢吞吐」的猜测——
用 `rpc.CallContext` 拿 `json.RawMessage`（不做解码）把两段分开计时，反序列化 68 MB / 11 万条只要 444 ms。

### 端点对比（必须同批量，否则结论会反转）

同批量 100 块、各 10 轮、同一区间：

| 端点 | 块/秒 | 条/秒 | 说明 |
|---|---|---|---|
| publicnode | 10.87 | 1,217 | 无限速，但单请求慢 |
| **drpc** | **23.70** | **2,644** | 快 2.2 倍，但受 3 次/秒限速（10 次请求理论下限 3.3 s，实测 4.2 s） |

**注意**：此前记的「publicnode 19 块/秒、drpc 2.5 块/秒」不可比——那次 publicnode 用 2000 块批、
drpc 用 100 块批。批量与端点混在一起，结论无效。

### 批量对比（publicnode，各 2000 块）

| 批量 | 块/秒 | 备注 |
|---|---|---|
| 100 | 10.9–41.1 | 固定开销占比高，波动大 |
| 200 | 18.3 | |
| 500 | 28.9（单轮 33.3） | 曾出现单轮 14.9 s 的异常 |
| **1000** | **32.7 / 46.1 / 48.4** | 三次中位 **46**，推荐 |
| 2000 | 16.7 | 响应约 125 MB，易触发 60 s 超时与重试，反而更慢 |

**推荐 `BATCH_BLOCK_RANGE=1000`。** 2000 块批在日志密度 90+ 条/块时，单次响应 125 MB、
经代理常触发 `context deadline exceeded`，重试让实际耗时翻倍。

### 一个未解释的环境差异

同一区间 1000 块，`curl` 直取只要 **4.9–5.3 s（13–14 MB/s）**，而 Go 的 `rpc.Client` 要 20–30 s
（2–3 MB/s）。已排除：

- **UA**：curl 伪装 `Go-http-client/1.1` 仍是 11.9 MB/s；
- **HTTP/2**：强制 ALPN 只保留 `http/1.1` 仍是 2.1 MB/s；
- **gzip**：压缩流 7.1 MB 反而只有 1.5 MB/s，且 Go 侧禁用压缩后请求直接卡死（超时被杀）。

剩余差异怀疑与本机代理对 Go 客户端 TLS 行为的处理有关，未定位到根因。
**它不影响上面的相对结论**（同环境下的端点/批量对比仍有意义），但意味着当前吞吐上限被代理压住了：
若直连可达 13 MB/s，全量索引的时间会从约 5 天降到 1 天以内。

### 复现方式

```bash
# 端到端（拉取 + 解码，不写库）
go run ./cmd/bench -margin 6000 -batch 1000 -rounds 3 -label publicnode

# 拆分传输与反序列化
go run ./cmd/bench -split -batch 1000 -margin 6000

# 换端点 / 换协议 / 关压缩
go run ./cmd/bench -split -batch 100 -rpc https://eth.drpc.org -label drpc
go run ./cmd/bench -split -h1 -batch 1000
```

工具只读 `contract_meta` 取 ABI，不写任何表，可反复跑。
